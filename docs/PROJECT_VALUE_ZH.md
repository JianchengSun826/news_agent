# Tech Newsroom Agent 的价值：与临时使用 Claude 写新闻相比

## 一、项目提供的核心价值

Tech Newsroom Agent 将 Claude 辅助写作组织成一套可以持续使用的新闻生产流程。它仍由人工使用 Claude 搜索、研究和撰稿，同时用本地程序保存选题记录、生成统一任务、检查结果身份、管理核验与修订状态，并整理最终文章和图片。

它的主要优势是让连续、多篇新闻生产更有秩序，减少重复选题、漏核验、文件混乱和旧稿误用。文章的质量仍取决于来源、模型表现和编辑判断，项目不能保证比直接使用 Claude 写出更好的单篇新闻。

**适合对外介绍的表述：**

> Tech Newsroom Agent 是一套保留人工把关的新闻生产工具。它把经审核的选题批量交给 Claude 研究和写作，再通过独立对话核验、图片权利确认和整批导出，形成可交付的新闻内容。系统保留跨批次去重和处理记录，完成后自动整理正文、图片并清理过程文件，让编辑把精力更多用于选题、核实与判断。

## 二、两种方式的实际区别

这里的“直接使用 Claude”，指每次临时发起对话，让 Claude 搜索新闻要点、撰稿，再由编辑自己保存和发布。编辑也可以手动建立同样的规范；项目的价值是将这些规范做成可以重复执行、部分能够强制检查的流程。

| 比较维度 | 每次临时使用 Claude | 使用本项目 |
| --- | --- | --- |
| 历史选题 | 编辑自行查询旧稿和聊天记录，判断是否做过 | 本地数据库保存历史事件，按公司、产品、事件类型、日期、核心事实和关键词进行去重比较；歧义由编辑处理 |
| 写作要求 | 每次重新描述要求，或自行维护提示词 | 统一任务文件携带当前选题、来源和输出要求，减少重复输入和遗漏 |
| 多篇处理 | 编辑自己分配任务、收集结果并核对是否齐全 | 整批交接，程序检查文章集合、必填字段、批次和请求身份，拒绝缺项、混批及过期返回 |
| 事实核验 | 由编辑主动安排，容易与写作混在同一轮对话 | 要求新对话独立核验，逐篇记录 PASS/FAIL；失败文章修订后必须重新核验 |
| 当前进度 | 依靠聊天上下文、文件名和个人记忆 | 批次首页显示状态、当前任务和下一步；未满足条件不能直接进入导出 |
| 修订材料 | 编辑自行保存版本、对应来源和核验报告 | 处理期间保留稿件与任务版本，核验结果绑定当前版本，减少旧结果套用新稿的风险 |
| 图片处理 | 编辑自行搜图、判断许可、保存署名 | 区分已核实候选与待确认线索，显式选择图片或无图，登记图片时保留权利和署名信息 |
| 结果整理 | 手动建目录、重命名、收集正文和图片 | 最终成果统一集中在批次目录，每篇一个文件夹；验证后自动清理该批次过程材料 |
| 长期记录 | 编辑自行维护选题、处理和发布台账 | 保留事件、核验结论、审批、权利和审计记录；真实发布 URL 可选登记 |

## 三、最值得保留的五项优势

### 1. 新闻生产积累历史，不依赖聊天记忆

单次对话能够完成一篇稿件，但持续运营需要知道哪些事件已经处理过。项目将历史记录保存在 SQLite 中，新批次可以与之前的事件比较，已完成的文章也可以被识别为复用内容。

例如，同一家公司的一次融资可能被多家媒体用不同标题报道。历史事件比较可以帮助编辑发现它们可能是同一选题，减少重新研究、写作和误发重复新闻的机会。当前去重使用确定性规则，并非完整的语义理解；相似事件、后续进展和不同命名仍需要人工判断。

### 2. 编辑要求成为固定交接，而非每次重新组织

研究简报、写作结构、来源标注、图片线索和返回格式由模板与当前任务文件共同定义。编辑上传文件即可交接整批工作，减少反复解释规则的操作。

程序能够检查输出结构、成员和身份是否正确。它不能仅凭字段齐全判断每个事实是真的，也不能保证模型严格遵守所有编辑要求；这些仍需要核验和人工审阅。

### 3. 核验成为必须完成的步骤

写作后交给一个全新 Claude 对话核验，可以减少同一写作上下文对判断的影响。每篇文章有明确的 PASS/FAIL，失败稿件进入修订与复核，当前有效文章全部满足条件后才能继续导出。

这种安排提供了流程约束，但第二个对话仍可能使用同一个模型、相同来源，并出现相同错误。PASS 表示这一轮核验通过，不能替代专业判断，也不是事实绝对正确的证明。

### 4. 将容易出错的文件交接交给程序检查

多篇稿件同时处理时，常见失误包括漏了一篇、导入别批次结果、用旧核验结果对应新版本，或者把未确认的图片当作最终素材。项目通过批次 ID、文章 ID、请求 ID、版本和状态检查降低这些操作风险。

这些检查具有明确价值：只要结果不符合规定，系统就会拒绝推进。编辑可以集中检查内容，而不必完全靠记忆维护每份文件之间的关系。

### 5. 完成后交付整洁，后续仍能去重

完成目录只保留每篇最终正文，以及有图文章的图片和许可记录；明确无图的文章只保留正文。批次过程文件在验证和数据库引用切换后自动清理，历史事件与必要业务记录继续保存在 SQL 中。

这符合“拿到新闻内容和图片即可完成任务”的实际需求。需要同时理解其边界：清理后不再保留原研究简报、完整核验报告、Claude 原始返回和历史稿件，不能宣称具备完整的原始证据归档。需要长期留存详细证据的业务，应另行设计保留策略。

## 四、一次批次工作的具体变化

以一次处理 8 篇新闻为例，直接使用 Claude 时，编辑需要自己安排各篇任务、核对结果、组织独立核验、对应修订版本，并收集最终文件。熟练编辑也可以一次批量处理，但需要自行维护这套约定。

使用项目时，流程为：

1. 审核候选 CSV，导入并处理去重歧义。
2. 将整批任务文件上传 Claude，导入研究与写作结果。
3. 在全新 Claude 对话中核验整批；失败稿件按任务修订并重新核验。
4. 为每篇文章确认图片或无图，完成一次整批登记。
5. 一次确认审核、批准和导出，获得集中整理的最终正文与图片。

目前实际完成的批次包含 8 篇无图文章，最终正文集中保存，过程材料已清理，去重记录保留。这验证了交付流程可以完成，尚不能据此证明比人工方式节省了多少时间，或提高了多少准确率。

## 五、适用场景与成本

项目更适合持续运营、经常一次处理多篇新闻、需要避免重复选题，并希望统一格式和核验步骤的个人编辑或小型团队。随着历史记录增加和操作规范稳定，历史查询与流程检查的价值会更明显。

如果只是偶尔写一篇新闻，且编辑已经有成熟的提示词、核验习惯和文件管理方式，直接使用 Claude 可能更省事。项目增加了 CSV 准备、结果 JSON 导入和状态推进等操作，也要求处理不符合格式的返回结果。两种方式的效率需要在相同质量要求下比较。

项目当前是本地、人工操作的 Phase 1.1 工具。程序不调用付费模型 API，但人工使用 Claude 的账户费用仍按实际服务计费。它不自动搜索网络、下载图片、上传 CMS 或发布新闻；也没有内置 Markdown 转 Google Docs、云端协作编辑或多人权限管理。Google Drive 文档交付是另一个待实施需求。

## 六、如何判断项目是否值得继续使用

建议在相近选题难度、文章数量、图片要求和核验标准下，分别记录直接使用 Claude 与项目流程的实际表现：

| 指标 | 记录方式 |
| --- | --- |
| 每篇人工投入时间 | 包括选题审核、提示输入、结果整理、核验、修订和发布准备 |
| 重复选题处理情况 | 记录发现的重复项、漏判和误判，并人工确认 |
| 交接与整理失误 | 记录漏篇、混批、旧版本误用及最终文件缺失 |
| 格式返工成本 | 记录返回结果导入失败次数及修复所需时间 |
| 最终质量 | 按同一编辑标准记录发布前事实修正、来源问题和发布后更正 |

现阶段可以明确说明的优势，是跨批次历史记录、统一任务、强制流程检查和集中交付。时间节省与质量提升应由实际运营数据支持，不宜给出尚未测量的百分比或承诺。
