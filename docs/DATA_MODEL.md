# Data Model

SQLite schema version 5 is created or upgraded by `newsroom init`. Existing v1/v2/v3/v4 databases are copied to `data/backups/` before migration. SQLite remains canonical; CSV, JSON, and Markdown are interchange or artifact formats.

Fresh initialization creates `data/` and its database/coordination files only. Batch preparation creates the current workspace directly; it does not require or create top-level `research/`, `articles/`, `images/`, or `output/`. This directory behavior changes no schema.

## Core records

`candidates` stores discovery metadata, normalized event fields, source URLs, duplicate state, selection state, audit timestamps, and `candidate_fingerprint`. The SHA-256 fingerprint canonicalizes event date, company, product, event type, core fact, and primary URL so a new CSV can reuse an old candidate.

`articles` links one candidate to at most one article. It stores workflow status, event metadata, current artifact paths, title/slug, `fact_check_outcome`, `revision_number`, selected `image_id`, publication data, and timestamps. `owning_batch_id` references the batch that first created an article and is immutable through the workflow. New articles created during batch preparation or duplicate inclusion store that batch ID; reusing an article never transfers ownership. The additive v3-to-v4 schema upgrade leaves this column null. Workspace migration may backfill it only when exactly one non-`REUSED_COMPLETE`, non-`EXCLUDED` `batch_items` relationship proves the historical owner. Zero eligible relationships remain unowned; multiple relationships or a conflict with a recorded owner block migration. Research, article, and fact-check files use `-vN.md`; current paths point to the active version.

`images` is the permanent publication record. Legacy manual/AI provenance is retained for recovery and archives. The supported batch path registers one selected local image or an explicit no-image decision per article. Batch-selected images copy `image_candidate_id`, rights basis, rights statement, landing page, creator, license, rights URL, and attribution so a publication package does not depend on transient model output.

`sources` is the domain reliability registry. `state_transitions` is the append-only actor/reason audit log.

## Batch records

`batches` stores `batch_id`, original filename and byte SHA-256, aggregate status, latest content request ID, latest fact-check request ID, and timestamps. `workspace_version` is a non-null integer recording the batch workspace layout version. Its schema default remains 0 for legacy or manually inserted rows requiring migration; `BatchWorkflow.prepare` explicitly records 1 for new batches created directly in the canonical Scheme C layout. Verified migration upgrades existing batches to 1 without changing workflow states. An identical file hash returns the existing batch.

`batch_items` links each batch candidate to its reused or new article. It records deterministic duplicate classification, batch-specific status, content version, and the latest actionable error. Important statuses are `WAITING_DUPLICATE`, `READY_FOR_CONTENT`, `CONTENT_IMPORTED`, `FACT_CHECKED`, `NEEDS_REVISION`, `REUSED_COMPLETE`, and `EXCLUDED`.

`batch_requests` is immutable handoff history. Each `req-...` stores type (`CONTENT`, `FACT_CHECK`, or `REVISION`), revision, request path, expected result filename, imported result path/hash, status, and timestamps. Identity plus exact membership prevents a stale or partial JSON from being applied.

`image_candidates` stores Claude search suggestions: article/batch IDs, landing and optional direct image URLs, creator, rights basis, license, original rights URL and statement, attribution, relevance, and review status. Allowed rights bases are `PUBLIC_DOMAIN`, `OPEN_LICENSE`, `OFFICIAL_PRESS_LICENSE`, and `OWNED`.

## Canonical workspace and ownership

Active batch-owned artifact and request/result paths remain repository-relative and point beneath `workspace/batches/OWNING_BATCH_ID/`; migrated unowned legacy paths point into `workspace/archive/`. Research, drafts, and fact-checks live in `articles/ARTICLE_ID/` as `research-brief-vN.md`, `article-vN.md`, and `fact-check-vN.md`; selected image bytes live alongside them as `hero.EXT`. Candidate metadata and image selections are retained in SQLite. `image-candidates.json`, batch/root README, and `batch-state.json` are derived views and can be rebuilt by `batch refresh-workspace`.

Requests use `claude/requests/content-request.json`, `fact-check-request-vN.json`, and `revision-request-vN.json`. Imported originals use corresponding `*-result*.json` names in `claude/archive/`; historical superseded requests may have an additional immutable request-ID directory. The request JSON's `output_file` is the result filename contract; inbox matching uses its declared identity, not merely the selected local filename. `claude/inbox/` is a manual drop location with no watcher or background imports.

`input/candidates.csv` preserves the original bytes and `source-metadata.json` its filename/hash. During migration the CSV copy is optional and must match the stored hash. `image-selections.json` is a resumable incomplete draft, not a canonical registration or approval. Only a complete, validated `BatchImagePlan` can advance every participating article in one transaction. `publish/ARTICLE_ID/` contains final package material; `publish/batch-manifest.json` maps the exact active article set to package paths and revision numbers.

`EXCLUDED` and `REUSED_COMPLETE` items are omitted from image/review/approval/publication membership. They are also ineligible evidence for migration ownership and never acquire or transfer ownership. Reused articles with non-null `owning_batch_id` retain that owner's files, and later dashboards link to them without transferring ownership. Legacy articles with no eligible active relationship retain null ownership and become read-only material under `workspace/archive/legacy-single-articles/`; unclaimed files are inventoried under `workspace/archive/unclaimed-files/` during migration.

Migration applies current release validation only to batch-owned articles. An owned `APPROVED` or `PUBLISHED` article must have exactly one active `batch_items` row pointing to its owner and retain current PASS, image/no-image decision, reviewed-material, and package checks; duplicate active rows in the same batch are also invalid. An unowned article with any active membership is invalid; inactive `REUSED_COMPLETE` and `EXCLUDED` rows neither claim ownership nor validate a package in the reusing batch. A truly unowned legacy publication package is immutable archive input: its bytes are plan/backup/staging bound and are not regenerated or upgraded. Legacy metadata may omit later schema fields, including `metadata.json.image_id` and `revision_number`. When present, image identity must exactly match the article value, including null; revision must match both the integer type and current value, so present null, string, Boolean, or wrong integer values are invalid. Path fields may retain old locations, the registered image may be absent, and package members may be optional. Identity fields and any canonical source bytes available on both sides must still agree.

## Whole-batch gates and durable recovery

Batch statuses include `WAITING_DUPLICATE`, `READY_FOR_CONTENT`, `WAITING_FACT_CHECK`, `NEEDS_REVISION`, `WAITING_REVISION`, `READY_FOR_IMAGE`, `REVIEWED`, `APPROVED`, `PACKAGED`, and `PUBLISHED`; a batch with only excluded/completed reused items may be `COMPLETE`. Fact-check PASS/FAIL remains per article. All participating articles must have PASS and be `FACT_CHECKED` before image registration; all must be `IMAGE_READY` for review, `REVIEWED` for approval, and `APPROVED` for packages or publication registration. Image registration sets article states to `IMAGE_READY`; the batch aggregate is not a replacement for these member checks. Packaging sets batch `PACKAGED` but retains article `APPROVED`.

Actor/reason transitions, URLs, and publication timestamps commit for the whole active set together. JSON publication results require `schema_version: 1`, the batch ID, and exactly one HTTP(S) `article_url` per active article. Request status is `PENDING`, `COMPLETED`, or `SUPERSEDED`; immutable request/result hashes distinguish idempotent imports from stale or altered input.

Workspace migration also produces local file records outside SQLite: a deterministic preflight, verified SQLite/archive/manifest backups, journals, a persistent access barrier, retained recovery inventories, and a success receipt or verified rollback proof. The saved plan records every article's projected owner, including explicit nulls; the manifest, journal, and receipt bind its digest. Execute rejects any database or relationship change after preflight and applies inferred owners in the same transaction as path and `workspace_version` updates. These records also bind database identity, canonical paths, file types/permissions/hashes, and complete old trees. No editorial state is advanced by migration. Terminal access revalidates projected ownership, immutable archive bytes, and retained snapshots while allowing active package material to evolve under ordinary batch gates. See [migration and recovery](WORKFLOW.md#9-旧工作区迁移与恢复) before handling these files; they are local recovery evidence, not generated dashboards.

## Identifiers and formats

Random IDs use `cand-...`, `art-...`, `batch-...`, `req-...`, `imgcand-...`, and `img-...`. `event_id` and slugs use lowercase ASCII with hyphens. Times are UTC ISO-8601. JSON model boundaries reject extra fields. CSV keywords and secondary sources use `|` separators.

## Optional images and batch index archival (introduced without changing schema v4)

`BatchImagePlan.items` accepts either the existing image selection or `{article_id, no_image: true, reason}` with a literal Boolean and nonblank reason, never both forms. Whole-batch membership and PASS checks remain mandatory. Both choices advance articles to `IMAGE_READY`, now meaning release material selection is complete. No-image articles retain null `image_id`; they do not create an `images` row. The `state_transitions` record with `entity_type=image_choice`, `entity_id=article_id`, `from_status=vN` and `to_status=NO_IMAGE` binds the explicit decision to revision N. Actor/reason and the ordinary article transition commit with the image plan. A new revision cannot reuse an old no-image decision. Derived views show `NO_IMAGE` instead of `MISSING`.

No-image packages omit hero, image-license.json and image-brief.md. Article metadata retains null `image_id`; the checklist states the editor chose no image. Package staging and owned-package migration validation reject image artifacts in a no-image package. Existing image-bearing packages remain compatible.

`BatchImageCandidateSupplement` accepts schema version 1, batch ID, and a nonempty subset of active article IDs, each with 1–3 validated candidate objects. It appends suggestions transactionally, deduplicates identical metadata, and records `entity_type=image_candidates`, `to_status=SUPPLEMENTED`. It cannot alter article content, revisions, checks, or immutable handoff bytes, and is available only before material selection.

Index archival is represented by append-only `state_transitions` entries with `entity_type=batch_visibility`, `entity_id=batch_id`, and `to_status=ARCHIVED` or `VISIBLE`. The latest entry determines root README placement. Batch status, ownership, paths, deduplication records and all material remain intact; archived batches can still be queried and operated by ID. This is visibility management, not deletion or migration. Missing canonical files still block access and must be restored from Trash or verified backups.

图片核验补充（Phase 1.1）：内容返回可选 `image_recommendations`（每篇最多 3 条），独立于已核实 `image_candidates`。推荐包含来源 URL、可空直接链接/作者/权利线索、verification_status（PAGE_INACCESSIBLE / INSUFFICIENT_EVIDENCE / RESTRICTED_USE）、非空 verification_issue 和 relevance。原始结果归档为推荐事实来源；不新增 SQLite 表或改变 schema。工作区生成 image-recommendations.json/md 审核视图及一次性 manual-image-candidates.json 可编辑草稿。人工补全适用授权后通过现有候选补充命令加入，记录 actor/reason；04 才确认实际图片使用。适用全站媒体政策可作为 rights_url，不要求独立逐图许可页。详见 IMAGE_POLICY.md。


## Completed-batch final-only retention (schema v5)

`batch_retention` is an additive table keyed by `batch_id` (FK to batches). It records constrained state `CLEANING` / `FINAL_ONLY`, repository-relative `delivery_directory`, a typed JSON `cleanup_manifest`, actor, reason and UTC created/updated timestamps. The manifest contains the batch ID, exact process files with SHA-256, process directories and the sealed final delivery inventory, including the export receipt. Its paths are confined to that batch; it is not a set of arbitrary deletion instructions. A v4 database is read-only validated using its original schema contract, backed up on explicit init, and upgraded to v5. Initialization does not delete batch files.

Action 05 validates final article/image/license bytes, then transactionally writes CLEANING and switches owned articles `draft_path` and selected images `image_path` to `workspace/completed/BATCH_ID/SLUG/`. Owned research/fact-check references and process image/prompt references are cleared. Requests keep IDs, statuses, expected result filenames, revisions and result hashes, but `request_path` becomes an empty string (existing NOT NULL column), and `result_path` becomes NULL. Empty request paths are legitimate only with an explicit retention record; readers return no request link rather than treating them as the repository root.

All candidates, articles, relationships, event fields, fingerprints, version and PASS/no-image decisions, rights, approvals and audit remain in SQLite. Retention audit uses `entity_type=batch_retention`. PACKAGED/PUBLISHED and APPROVED/PUBLISHED retain their existing meanings. Process-tree deletion succeeds before state advances to FINAL_ONLY; a failure leaves the durable CLEANING inventory and final references for retry. Unknown or changed remaining files and symlinks block further deletion. Cross-batch file references block preflight. No backups or external originals are removed.

Final-only batches need no source CSV, process views, launchers, typed request files or full publication packages. Refresh rebuilds only the root index, and status/duplicate reuse links to final materials without recreating the batch tree. Full-package creation and historical content imports are closed; optional publication URL registration remains supported. Migration validation checks final inventory, references and ownership instead of requiring deleted inputs. CLEANING supports terminal access checks, but migration preflight requires finishing cleanup first. The previous complete-delivery layout remains available until an explicit export applies retention.
