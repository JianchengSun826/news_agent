# Phase 1.1 人工文件编辑与变更登记设计

状态：待用户审阅；尚未实施。

## 目标和约束

用户希望用自己习惯的编辑器手动修改日常新闻文件，再由程序显示差异、登记修改、保存历史并同步状态。允许人工改稿、补来源、改标题、换图片及调整署名；保留独立核验、人工审核、批准和人工 CMS 上传。

这是当前 Phase 1.1 的本地编辑能力。SQLite 仍是已登记状态来源。程序只做确定性比较和验证，不判断修改是否改变新闻事实，不调用模型或网络，不监听文件、不增加后台进程。真实批次的操作仍由用户执行。

本次覆盖已导入内容、尚未发布的批次。已发布版本、原始输入、交接归档、核验结论和批准记录保留为历史；已发布新闻的更正版本与 CMS 更正记录不在本次实施范围。编辑前仍须先恢复已经丢失的规范素材，不能绕过迁移恢复要求。

## 方案选择

采用“可编辑文件 + 明确登记”的方式：在文章目录提供固定名字的工作文件，登记时生成新的规范版本。优点是可以反复保存、撤销、取消，不覆盖历史稿件；代价是修改后需要一次登记操作。

不采用直接覆盖 `article-vN.md` 再补救：覆盖前的字节可能已丢失，旧核验和批准无法证明对应哪个文本。不采用实时文件监听：它不符合当前人工触发阶段，也不能决定保存到一半的文件是否可登记。

“直接编辑”指下面的日常工作文件，不要求用户先生成新的 Claude 返回 JSON。历史版本与系统记录不是工作文件。系统提供从旧版当前稿件建立工作文件的入口。

## 可编辑范围

| 文件 | 编辑内容 | 登记规则 |
| --- | --- | --- |
| `editable/articles/ARTICLE_ID/article.md` | 正文、Markdown 标题、来源列表 | 内容变更产生新稿件版本，重新独立核验 |
| `editable/articles/ARTICLE_ID/research-brief.md` | 研究、证据、背景与未知事项 | 内容变更产生新版本，重新独立核验 |
| `editable/articles/ARTICLE_ID/metadata.json` | `title_cn`、`slug`、`primary_source`、`secondary_sources`、`summary`、`notes` | 标题、slug、来源、summary 变更重新核验；notes 仅更新编辑笔记 |
| `editable/articles/ARTICLE_ID/image-candidates.json` | 新候选、候选权利信息及资料图说明 | 用原候选 schema 验证，追加候选；不覆盖已有永久权利记录 |
| `editable/articles/ARTICLE_ID/image-selection.json` | 保留当前图片、选择无图、选择候选并指定本地新图片；理由与权利确认 | 图片选择变化重新审核和批准，不要求未改动文本重新核验 |
| `editable/notes/` | 个人笔记和补充材料 | 可任意新增、修改、删除，不推进状态、不进入发布包 |

`metadata.json` 仅包含允许编辑的字段；ID、拥有批次、状态、版本、核验结果、批准、时间、数据库路径及发布 URL 不作为可编辑字段。未知字段拒绝并指出位置。标题以 `title_cn` 为登记标题，程序不自动从 Markdown 抽取或修改正文标题。

工作区图片选择使用明确的 `KEEP`、`NONE`、`REPLACE` 模式：KEEP 校验已登记图片的哈希和权利；NONE 需要非空理由；REPLACE 包含完整候选权利对象、editable 内的本地图片相对路径及显式 `rights_confirmed: true`。更正当前图片的署名或权利信息也使用 REPLACE，可继续使用相同图片字节，但生成新的权利记录并要求重新确认。候选清单的编辑只追加建议，不隐式改动已经选定的图片。

初始候选的事件日期、公司、产品、事件 ID 与指纹保持原记录；本次不通过人工 metadata 改变事件身份或去重结果。确实选错事件时应返回候选/选题步骤，不能把原候选无审计地改成另一个事件。

README、`batch-state.json` 和文章目录原有的 `image-candidates.json` 仍是可重建视图，刷新会覆盖。个人笔记放入独立的 notes 目录，不把笔记写进生成视图。系统保留原始 CSV、`claude/archive/`、核验报告及迁移备份，不从这些历史文件反向同步编辑结果。

## 文件与交接记录

批次新增 `editable/` 工作区，用户始终编辑固定文件名。每次准备产生一个 `MANUAL_EDIT` 交接记录，使用已有 `batch_requests` 表，不增加表或升级 schema v4。新增 Pydantic 模型定义该类型的 request/result，迁移和交接校验需显式支持它。

request 位于 `claude/requests/manual-edit-request-vN.json`，result 位于 `claude/archive/manual-edit-result-vN.json`。目录沿用现有交接布局，但这些是本地人工编辑证据，不交给 Claude。N 是人工编辑交接序号，不等于任何单篇文章的 revision。

request 保存全部有效文章的 ID、拥有批次、基础版本、允许编辑的元数据、基础正文/简报及 SHA-256、图片选择、权利记录和图片字节哈希。工作区中的说明文件告诉用户哪些文件可以编辑；基础 request 不供编辑。request/result 的 batch、request、output 身份及文章集合严格一致，result 原始字节哈希保存到 SQLite。

result 由程序依据工作文件生成，包含登记后的完整文本/元数据、变更类别、变更前后哈希、图片选择以及图片归档引用。它是后续版本的历史证据，不替换内容或核验交接的原始结果。所有文件引用是根目录下的相对路径；JSON 直接链接仍按 HTTP(S) 校验。

同一批次只允许一个未结束的人工编辑交接。已有工作文件绝不因重复准备或刷新被覆盖；重复准备打开已有编辑区，基础内容发生变化时报告冲突。取消关闭该交接，保留工作文件和旧版本供用户查看，不把用户修改删除。

## 人工操作入口

保留现有八个 Finder 操作，追加两个：

1. `09-准备并打开人工编辑区.command`：建立基础快照和可编辑工作文件；已有编辑区则打开，不覆盖。Terminal 显示编辑路径和状态。
2. `10-登记人工修改.command`：校验全部工作文件，打开差异报告，显示受影响文章、是否需重新核验及批次闸门变化，用户确认后一次登记。

CLI 对应：

```text
newsroom batch edit-prepare BATCH_ID
newsroom batch edit-preview BATCH_ID
newsroom batch edit-apply BATCH_ID PLAN_JSON --actor editor --reason "人工编辑"
newsroom batch edit-cancel BATCH_ID --actor editor --reason "取消本次编辑"
```

preview 是确定性计划与差异报告，不改变文章状态；允许保存报告。apply 必须使用仍与当前数据库、基础快照、全部工作文件及本地图片哈希一致的计划，不能先确认一份差异再应用另一份文件。取消确认不登记。只有 notes 改动或完全没有新闻素材改动时明确显示，无需制造新稿件版本或新的事实核验任务。

01 只定位模型交接，02 只导入模型结果；它们不会把 MANUAL_EDIT 当作 Claude 任务。批次 README 另外显示待登记人工修改。03 同时提供规范稿件和编辑区链接，并标明哪个是当前已登记版本。

## 状态失效规则

程序根据字段和字节比较分类，不让用户用“只是润色”等说明保留旧核验。

| 修改类别 | 文本版本及核验 | 图片选择 | 整批审核、批准与发布包 |
| --- | --- | --- | --- |
| 正文、简报、标题、slug、来源、summary | 修改文章 revision +1；清除当前核验结论，进入 DRAFTED；生成新的独立核验任务 | 旧选择保留历史，但新内容版本需重新确认图片或无图 | 全部有效文章的当前审核和批准失效；旧发布包保留为过期历史，不能用于发布登记 |
| 图片替换、改为无图、权利或署名变化 | 保留未修改文本版本及 PASS | 创建新的永久图片记录或当前版本无图选择，不改写旧记录 | 整批重新审核、批准及打包 |
| 仅补充未选图片候选 | 保留版本与核验 | 只追加验证通过的候选，不改变当前图片 | 不撤销对未改变素材的批准 |
| 仅 notes 或个人笔记 | 保留版本与核验 | 不变 | 不推进或撤销状态 |

受影响文章之外的 PASS 保留；新的事实核验 request 只包含文本/来源发生变化的文章。只要任何有效文章尚待核验或 FAIL，整批仍不能审核、批准、打包或登记发布。

核验 request 的序号与各篇 revision 解耦，按该批次既有核验交接序号递增；每项仍记录其真实稿件 revision。避免只修改某一篇时覆盖已有 request/result 文件。原有 pending 核验或修订任务在登记修改时标为 SUPERSEDED，保留文件，旧返回结果拒绝。未改变且仍待核验的文章并入新的当前任务，不能因为任务被替代而丢失核验。

图片选择继续保持整批原子确认，但支持保留仍有效的既有选择并处理待选择项；合法的“部分文章保留原图、部分待重新选择”不再作为旧数据损坏。保留项必须与当前图片字节、权利、文章归属及版本相符。新图使用唯一文件名，禁止覆盖旧图，发布包仍导出 `hero.EXT`。

进入 REVIEWED/APPROVED 的是本次完整有效文章集合；所有旧批准只作为审计历史。登记编辑后批次根据成员重新计算下一步，不沿用 PACKAGED 状态。外部 CMS 不受本地编辑影响，也不自动更新。

## 防止未登记修改沿用旧批准

准备编辑区时建立完整基础快照。检查变更通过人工 preview 或后续关键操作触发，不靠后台监听。

核验结果导入、图片登记、审核、批准、打包、发布登记前，对存在编辑交接的批次检查未登记改动；存在新闻素材变更时停止并提示登记或取消，不能拿新文件继续使用旧批准。notes 不阻塞。

规范稿件、图片和权利记录的当前字节/元数据也需与其已登记证据一致。原始 Claude 内容从已验证返回文件取得；人工版本从已验证 MANUAL_EDIT result 取得。检测到用户直接覆盖规范 `*-vN.md`、已登记图片或系统记录时给出具体路径和“把修改保存到编辑区再登记”的指引，不静默恢复或覆盖用户字节。

首次打开旧批次依据其已登记交接建立基础；如果当前素材已与记录不符，先生成冲突报告并保存用户字节，不把未知修改自动认作历史基线。CLI 内容/修订/核验导入也建立或更新对应的登记证据。迁移准入继续验证不可变历史和路径安全，不让一份未登记工作草稿阻塞只读诊断；发布闸门负责拒绝未登记变化。

## 原子性、恢复与冲突

prepare、apply、cancel 使用独占 operation lock，普通 Finder/CLI 不可同时修改基础；锁入口避免在已持有共享锁的 `_room` 生命周期里升级锁。编辑器不受 flock 控制，因此 preview/apply 仍必须重新读文件并验证全部哈希。

全部输入先通过 Pydantic、URL/slug、精确成员、归属、当前版本、路径和文件类型检查；不跟随符号链接，不读取根目录外的本地图片，外部下载图片先由用户复制进 editable 目录。格式错误或冲突列出 article 和文件位置，整批拒绝，不部分更新。

apply 把新版本、图片和 MANUAL_EDIT result 暂存到同一文件系统；旧稿件、旧图、旧包和全部用户编辑文件不覆盖、不删除。持久操作记录绑定计划、文件哈希及事务提交标记，采用访问屏障直到新文件和数据库指针均完成；图片或正文的旧路径一直保持可恢复。数据库状态、成员、审计和交接更新一次事务提交。

人工编辑使用独立的 `data/manual-edit-journals/` 和 `data/manual-edit-lock.json`，不改写现有迁移 journal/barrier。普通 CLI/Finder 准入检查两类屏障，人工编辑恢复入口只放行其绑定操作；迁移执行拒绝未完成的人工编辑事务。工作区内有尚未登记的可编辑文件本身不等于恢复屏障，只有 apply 的未完成持久事务才阻止常规访问。

提交前失败清理或保留未引用的新暂存，数据库和旧包不变。提交结果不确定时拒绝再次登记，检查持久标记和数据库事实后恢复；不能仅依赖进程内 try/except 宣称崩溃安全。提交后刷新视图失败明确报告“修改已登记，视图待刷新”，不能提示重新登记并重复加版本。恢复保留用户编辑文件和新旧素材，现有迁移恢复屏障仍优先。

apply 完成后下一次准备从新规范版本建立新的编辑基线；不能把仍含上一轮内容的 editable 文件覆盖成新基线而不保存。重试相同已提交计划返回原结果，不增加版本或审计；不同内容需要新的编辑交接。过期计划必须重新 preview。

## 实施组件和验证

新增独立 `manual_edit.py` 处理准备、差异、分类、登记和恢复，避免把整套编辑逻辑塞进 batch.py。现有 batch/workspace/macOS/CLI 接入入口和提示；批次发布服务增加未登记变更检查，并支持已有有效图片选择。交接模型、迁移类型校验、核验序号和状态汇总同步修改。输入验证、状态计算与持久写入分离。

更新 WORKFLOW、WORKFLOW_ZH、ROADMAP、DATA_MODEL、IMAGE_POLICY 和 README，明确哪些是可编辑工作文件、哪些是历史与派生视图。没有 schema 变化，不执行真实 init/迁移或真实批次登记。

先写失败测试，使用临时目录和真实 SQLite：

- 整批部分改稿产生正确版本和核验集合，未改文章 PASS 保留。
- 标题/来源/简报改动重新核验；notes 不产生假版本；无变化重试幂等。
- 图片替换/无图/署名更正保留文本 PASS，但撤销整批批准；混合既有和新选择原子处理。
- 原始交接、旧版本、旧权利记录和旧包字节保留；canonical 外部改动阻止沿用旧批准。
- preview 后编辑、版本变化、重复成员、外部文章、非法 slug/URL、路径穿越和符号链接全部拒绝。
- 旧 pending 核验/修订结果不能应用到新版本；核验序号不覆盖历史。
- prepare/取消/失败不丢用户文件；数据库异常、进程中断和刷新失败有可验证恢复结果。
- MANUAL_EDIT 原始哈希、精确成员、归属、迁移验证和仓库搬迁兼容。
- Finder 准备、差异确认、取消和结果提示不把人工文件误作模型任务。

执行完整 pytest 和隔离离线 demo。另用合成批次演示“写作导入 → 人工改稿 → 新核验 → 图片或无图 → 审核批准 → 新发布包”，不修改真实批次。

验收标准：用户无需手工生成模型返回 JSON 或修改数据库即可完成日常编辑；程序展示实际差异，保留历史，按规则失效旧核验/批准，能够从失败中恢复；新功能不削弱旧迁移保护，不增加 Phase 2 自动化。
